# Starbook v1.5.1 — Project Governance & Agent Handoff

## 1. 版本目标

将 Starbook 当前已经形成的开发、数据、发布、扩展和 Agent 协作规则正式固化进仓库，让后续新的 Agent 窗口无需依赖旧聊天记录即可恢复项目上下文，并把“每版必须记录链路变化”变成 CI 可检查的项目规则。

本版不以新增周年视觉功能为目标。

## 2. 用户可见变化

- 产品统一标题为《星屿之书》。
- 登录、魔法书、导航等既有视觉/交互结构不变。
- 当前 Book 的 Supabase `books.name` 同步更新为《星屿之书》，因此状态栏等依赖 Book Context 的位置也使用统一名称。

## 3. Runtime 链路变化

无变化。

继续保持：

```text
Auth → SB.user → SB.book.current → SB.store → Scene Runtime
```

并继续保持：

- `SB.book` = 数据 Book Context；
- `SB.magicBook` = Magic Celestial 视觉控制器。

## 4. 架构 / 扩展契约变化

运行时代码无变化，但新增正式的 `docs/ARCHITECTURE_EXTENSION_CONTRACT.md`，把以下长期约束从聊天/隐含约定升级为仓库契约：

- 多用户；
- 多 Book；
- Relationship / Theme / Experience 解耦；
- Memory First 长期方向；
- 当前 JSONB 仅为 Anniversary Bridge；
- 当前唯一 Magic Celestial / World Map 不得写死为平台唯一能力。

## 5. Auth / Membership / RLS 变化

RLS policy 本身无变化。

当前 Book 新增两名 active editor：

- `11aa32fe-3875-4880-81fb-02a543dca853`
- `62adee54-c59a-4844-abb5-1b5629da3bf9`

Owner 权限保持不变。成员通过 `book_members` upsert，不在前端写死。

## 6. 数据模型 / Migration 变化

Schema 结构无变化，`schema_version` 仍为 1。

新增非破坏性 migration：

`supabase/migrations/002_v151_title_and_members.sql`

它只做两类变更：

1. 将固定 Anniversary Book 的 `books.name` 更新为《星屿之书》；
2. 将两名指定 Auth User upsert 为该 Book 的 active editor。

它不会修改 `book_data.payload`、不会清空数据、不会重新 seed、不会删除任何 Storage 对象。

## 7. Storage / Media 变化

无变化。

继续使用 Private Bucket `starbook-media`，资源归属于 Book。

## 8. Git / Branch / PR / Merge 链路变化

正式将以下流程写入仓库治理规则：

```text
release/vX.X.X
→ PR to main
→ validate-starbook
→ Auto-merge / approved merge
→ main
```

`main` 被定义为唯一 Production branch。

## 9. CI / Validation 变化

增强 `tools/check_project.py` 和 `validate.yml`：

- 检查治理文档存在；
- 检查 `VERSION` 格式；
- 检查当前版本 Release Record 存在；
- 检查 CHANGELOG 包含当前版本；
- 检查 PROJECT_STATE 声明当前版本；
- 保留 build、JS syntax、namespace ownership 和 Secret marker 检查。

因此未来“只改代码、不记录版本链路”的 PR 将无法通过完整校验。

## 10. GitHub Pages / Production Deploy 变化

治理规则明确为：

```text
main
→ Deploy Starbook to GitHub Pages
→ site/ artifact
→ Production URL
```

Production URL 不因版本分支变化而变化。

本版包含 `deploy-pages.yml` 的 main-only 生产配置，便于新 Agent 看到完整链路。

## 15. 用户需要手动操作

代码发布仍按现有 release pipeline。

此外，本版上线后需要在 Supabase SQL Editor **整段运行一次**：

`supabase/migrations/002_v151_title_and_members.sql`

运行前确认两个新增 UID 已存在于 `Authentication → Users`。Migration 可重复执行，且不会触碰已有回忆数据。

发布 v1.5.1 时：

```powershell
.\publish.ps1 -Version 1.5.1 -Message "项目治理与 Agent 全链路交接"
```

若当前工作已直接位于 `release/v1.5.1`，脚本将使用该分支继续发布。

## 15.1 发布脚本兼容性修复

修复 Windows PowerShell 下 `publish.ps1` 的 Secret 扫描兼容问题：空的 `site/.nojekyll` 会导致 `Get-Content -Raw` 返回 `$null`，从而在 `.Contains()` 调用处中断发布。现在仅扫描部署目录中的文本资源，并显式跳过空内容；不降低高风险 Secret marker 扫描能力。

## 16. 测试与验证

必须通过：

```powershell
python build.py
python tools/check_project.py
```

以及 GitHub PR：

```text
validate-starbook
```

本版重点验证 CI / 文档一致性。运行时代码只涉及版本标识与 Book 名称文案，不改变场景逻辑。

Supabase 基础初始化不需要重跑；只运行新增的 v1.5.1 非破坏性 migration。

## 17. Production 数据影响

- 是否需要重新导入旧数据：**否**。
- 是否需要运行 SQL：**是，仅运行一次 v1.5.1 非破坏性 migration。**
- 是否修改 `book_data.payload`：**否**。
- 是否删除/覆盖现有回忆或 Storage：**否**。

所有已有城市、回忆、照片、音乐继续存在同一个 Supabase Project / Book 中。

## 18. 已知问题

沿用 v1.5.0 的 runtime 技术债：

- `book_data.payload` 仍为 Bridge JSONB；
- Memory 仍与 City 有 V1 耦合；
- Theme / Experience 尚未真正插件化；
- Realtime / PWA 暂未实现；
- 图片仍为单一尺寸。

## 19. 回滚方案

本版没有 schema 结构变化。代码可通过 revert v1.5.1 merge 回滚，已有回忆数据不受影响。

若只需撤销标题/成员变化，应使用新的向前 SQL 明确改回名称或调整 `book_members`，不要 reset 数据库。
